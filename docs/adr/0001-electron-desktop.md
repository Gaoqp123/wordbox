# ADR-0001：桌面端用 Electron，不用 PWA

- 状态：已接受
- 日期：2026-10-04
- 规划条目：§2 D1
- 关联：ADR-0012（取词程序无关）、ADR-0009（不做手机端）

## 背景

核心场景是"在任何程序里选中一个词，按一下快捷键就看到释义"。这一句话把能力清单钉死了：
全局快捷键、读系统剪贴板、托盘常驻、直连本地全量词库、断网可查可复习。

最初的 v0.1 方案是 PWA：一门语言、零安装、天然跨平台。但网页运行在浏览器沙箱里，
上面五件事一件都做不到——网页拿不到系统级快捷键，也读不到别的程序里的选区内容。

## 决策

用 Electron 做桌面应用。主进程持有系统能力（快捷键、剪贴板、文件、数据库），
渲染进程只负责界面，preload 作为两者之间唯一的白名单通道。只维护一门语言。

## 备选方案

- **PWA / 纯网页**：跨平台、零安装，但全局快捷键、跨程序取词、本地全量词库均不可行。
- **Tauri（Rust）**：安装包更小、内存更省，但要引入第二条语言链路，而取词这类系统交互并不会更省事。
- **原生 Win32 / .NET**：系统能力最强，但开发与迭代成本远高于收益。

## 后果

- 好：所需系统能力全部有现成 API；一门 TypeScript 贯穿三层；生态成熟，AI 协作踩坑少。
- 代价：安装包 250 MB 量级；常驻内存高于原生方案。
- 代价：模拟输入能力受操作系统与安全软件约束，这一点后来被 ADR-0014 的实测证实。

## 复核触发条件

- 手机端复习上升为核心诉求（届时可能回到"PWA + 导出数据"的组合，见 F-22）；
- 安装包体积或常驻内存成为真实的使用障碍。
